ANALYSE Why the software never got built

Five whys · cause & effect · the root

Five whys

ProblemThree weeks in, zero running software.
Why 1Building couldn't start until the specs were "complete".
Why 2Because the rule is docs-before-code, and the list wasn't finished.
Why 3Because the list kept growing — every gap found while writing spawned a new document.
Why 4Because gap-discovery routed to authoring, never to an experiment.
Why 5Because "done" was defined per task but never for the phase.
Root cause. The process had a definition of done for tasks and no exit condition for the specification phase. A phase that can't end doesn't — so effort pooled in the only step allowed to run.

Contributing causes

Method

  • No phase exit criteria
  • No spec-expiry rule
  • Gaps → docs, not spikes

Measurement

  • Progress = files written
  • Validation checks form, not depth
  • No customer metric

People

  • Two, part-time, no lanes
  • Builder never invoked
  • All decisions to one approver

Materials

  • No price
  • No customer input
  • Schema as prose

Machine

  • No compiler (until now)
  • No eval harness
  • Migrations never run

Environment

  • Nobody downstream waiting
  • No deadline on anything
  • Scope written as if hours were unlimited
Strongest cause: "nobody downstream waiting." A process with no one expecting its output drifts to the cheapest, least-exposing step. Every countermeasure below works by installing someone who waits.

CONTROL Keeping it from sliding back

Control plan · the signals that fire
ControlSignalFreqReaction rule
Newest-file ruleType of the latest commitWeeklyTwo weeks of .md in a row → stop, re-cut. Don't push harder.
Capacity checkHours worked vs gate estimateWeeklyTwo weeks under 60% → shrink the gate, don't extend it silently
Phase exitNamed condition metPer gateNot met → decide, don't drift into the next gate
Golden pass rateScore on 30 questionsPer prompt changeBelow 80% or any safety fail → revert the change
Cost / conversationThree-number modelWeeklyAbove $0.025 → check model tier before anything else
Cost capConversations over $0.40ContinuousHard stop mid-conversation; log incident
Tenant isolationCross-tenant read succeedsPer deployAny occurrence → block deploy, P0
Spec expiryDays unimplementedMonthlyOver 60 → move to /archive
Design intent: almost every control is automatic once built — an eval score, a cost cap, a queue-age alert. Only the phase exit needs human judgement, deliberately, because the failure being corrected was a judgement made repeatedly under no pressure. A rule agreed while fresh beats a call made at 11pm.

Weekly checkpoint — 30 minutes, same day

1 · What actually ran this week?  ·  2 · What did the hours really come to?  ·  3 · What's blocked, and who owns unblocking it?

If someone missed a week, say so — no apology expected. The plan is sized for 20 hours and survives a bad fortnight. It does not survive someone quietly stopping and neither of you saying it.
